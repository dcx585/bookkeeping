## 🔴 修掉的 3 个真 Bug

### BUG-1 「充100实付96 → 记成196」的根因没修干净
用户之前报过这个 bug，当时的修法是加 `sort()` 把银行条目排前面。
**自检发现：合并成功是靠排序"碰运气"，不是判据本身成立。**

证据：把 `sort()` 去掉后，同样两条数据立刻退回 `[100]`（合并成面额，金额错）
或 `[96,100]`（根本不合并，记成196）。

真正的问题在两处：
1. `isRechargeItem()` 写了「账户是银行卡 → 直接 return false」，
   把「尾号2374卡**充值**话费100元」这类**银行渠道的充值通知**排除在"面额侧"之外。
2. `isBankItem()` 只认"银行卡/尾号/卡号/人民币"，银行短信写得"素"一点
   （如「您9月19日支出96.00元」）就认不出，配不上对。

**修法：**
- 两个函数改成**互斥**（先判充值/缴费意图，是则不算银行实付侧；反之亦然）
- `mergePool` 的配对改成**对称判断**：不管谁先谁后，
  只要「一条是面额侧、一条是实付侧」且实付在面额 50%~100% 之间 → 同一笔
- `isAlreadyBooked` 同步用同一套判据（避免"框里去重了、入账时又重记"）

验证：5 种面额/实付场景 × 正序逆序 **全部合并为实付 96**（详见 regress.js R1）

### BUG-2 通知队列用正则读 JSON → 正文含花括号就丢通知
`NotificationReaderService` 的 `queueAck` / `queueRead` / `markSeen` / `nkeyInSeen`
4 处都用 `Pattern.compile("\\{[^\\{\\}]*\\}")` 从 JSON 数组里抠对象。

**这条正则在遇到通知正文含 `{` 或 `}` 时会断裂。**
实测：`[{"id":"b1","text":"客户{张}消费96元"},{"id":"b2",...}]`
→ 抠出的是 `{张}` 和 `,"nkey":"n1",...}` 两段碎片，`b1` 的 `id` 直接丢了。

**后果**：那笔已经入账的通知永远 ack 不掉 → 队列里残留 →
待处理框反复出现同一笔（用户抱怨过"记了又回来"，这可能就是其中一条暗线）。

**修法：** 写 `jsonObjects()`，做**花括号配平 + 字符串/转义感知**的逐字符扫描，
4 处全部换掉。任意嵌套、任意括号、转义引号、emoji、未闭合数据都安全
（Java 侧 10 项测试全过）。

### BUG-3 额度提升通知被记成支出（假账）
「【支付宝】您的花呗额度已提升至5000元」→ 被判定为支付，
**金额 5000 记成一笔"还款"支出**。

根因：`payWord` 命中"花呗"，`findAmounts` 又能抠出 5000，
而"额度"类通知不在任何排除规则里。

**修法：** 在 `looksLikePaymentText` 加一条——
出现「提额/额度/可用额度/授信/限额」且**没有**「已支付/已扣款/已消费」等
"钱真动了"的完成语 → 判为非支付。

验证：10 种额度话术全部剔除；5 种真实还款/消费（已还款5000、花呗还款成功…）**没被误杀**。

## 🟡 一并收紧的风险点

**`isAlreadyBooked` 在时间不可比时"放宽为匹配"**
原写法 `if(!t||!rt) return true;` —— 意味着只要金额相同，
哪怕没有时间信息就认定"已入账"，可能**静默吞掉一笔真实的新消费**。
改为时间缺失时**不**放宽（同额本身已是信号，不该由"缺时间"额外放大）。
