> 借鉴自 [blue-whale-keeper](https://github.com/a2244921700-code/blue-whale-keeper)（蓝色大肥鱼管家）

## 一轮做了什么

把「按动作词附近找数字」换成「**按来源认货币锚点**」。

旧做法：一条大正则找「支付/消费…附近的数字」。
新做法：先判断是哪家（微信/支付宝/银行/电商），再认各自的锚点。

| 来源 | 锚点 | 为什么 |
|---|---|---|
| 微信 | `¥` | 通知必定带这个符号 |
| 支付宝 | `元` | 标准句式「你有一笔X元的支出」 |
| 银行 | `人民币` 优先，退回 `¥` | 卡号、余额不会带这两个标记 |
| 电商 | `实付/付款金额/订单金额` 优先，退回 `¥` | 通知里有多个 ¥（总额/红包/优惠券） |

这样 `[48条]`、6 个积分、「领1元红包」这些干扰项天然被排除。

## 借到的几个关键判断（都是真机踩坑踩出来的）

1. **「支付宝」里藏着「支付」** → 判方向前先洗掉品牌名，判不出来就放弃。
   原则：**错账比漏账难发现得多**。

2. **转账/红包本身没有方向** → 用短语判断，且**收入短语必须优先**。
   「转账给张三」是支出，「张三向我转账」是收入，只看词必然判错一半。

3. **银行支出降级为待确认**，不丢弃也不直接记。
   它多半与支付宝/微信重复，但也可能是只走卡上的自动续费。

4. **未来时态不进账** ——「将于明日扣款」不是已发生的交易。

5. **收支词打架时放弃** ——「已支付 ¥30，退款到账」这种，宁可漏记。

## 怎么开关

**在 App 里点**：「更多 → 🔍 解析诊断」

面板顶部显示当前引擎，一键切换，设置会持久保存（重启 App 依然有效）。

**改代码**：`app.html` 里搜 `window.PARSE_V2`。默认已是 `true`。

```js
window.PARSE_V2 = true;   // 默认开启
```

- **开启（默认）**：走新解析器，v2 抛异常时自动回退旧逻辑
- **关闭**：完全走旧逻辑，零风险

## 解析诊断面板能做什么

这是这次顺带做的一个真正有用的工具。

以前的问题是：「**收到了但没记上**」和「**压根没收到**」看起来一模一样，
但一个要去改解析规则，一个要去查通知权限 —— 完全不同的处理方式。

现在贴一条通知原文进去，立刻告诉你：

```
来源：微信
金额：4.85 元
方向：支出
✅ 这条能正常记账
```

或者：

```
来源：支付宝
金额：20.00 元
❌ 不会记账
原因：有金额 20 元，但判断不出收支方向
```

**下次微信不记账的时候，别猜，贴原文进来看。**

## 已知局限

- **没有真实样本库**。`imported_tx.json` 是空的，所有验证靠金标准那 8 条短信用例
  + 从对方 README 抄的踩坑文本。**真机跑过才算数。**
- 对方项目才 8 star、创建 13 天，作者自己也在高频修 bug。
  规则可以借，但别当标准答案。
- 没做「证据融合」。那是第二步的事：一条支付会同时留下银行通知 +
  支付宝通知 + 支付页，它们应该融合成一条，而不是靠指纹互相拦。

## 下一步（如果这轮验证有效）

按 blue-whale-keeper 的 `IngestPipeline.kt` 重写判重：
- 不同来源的同额同向 → 视为同一笔，补全信息而非丢弃
- 同来源内才用商户名区分（「A店花20」不该吞掉「B店花20」）
- 墓碑机制：用户删过的记录不再重建
- 时间窗：普通 60 秒，银行 10 分钟
